# AIS-HARNESS-3: run-engine contract (12 properties)

Wave 3.5 (plan `.specs/plans/AIS-HARNESS-3.md`, section "Wave 3.5"). Threat model: accidental or buggy workers only; deliberately hostile dispatched code is out of scope, and a finding that needs it is dispositioned `reject: out of scope (threat model)`.

**Frozen.** The meanings below are the contract. The Wave 3.5 harness does not check every meaning in full: after every command the independent oracle (`skills/ship-ticket/scripts/engine-oracle.test-helper.mjs`) checks exactly what the "Oracle check" column lists (P10 is checked by `engine-crash.test.mjs`, not by the oracle), and "What the Wave 3.5 harness does not show" below lists the parts it leaves unchecked. A property may not be weakened, nor an exception added, to make a test green: that needs an owner decision recorded here. An exception covers only the case it names. A known limit (D1-D7 below) is a disposition, not a pass: it keeps its severity and failed property.

"Command" means one `run-engine.mjs` CLI invocation (`init`, `status`, `drive`, `resume`, `mark`, `clear-unit`, `gate red|review|ship-ready|unit-review`). "Owner line" means a RUN-STATE line appended between commands while no dispatched code could run. "Oracle" means the independent test oracle: it decides from files on disk, raw `state.json` fields, `runs.log`, exit codes and RUN-STATE text, and never calls `unitStates`, `reviewStates`, `ceiling` or another engine decision function.

## Observation for the owner (not dispositioned)

A unit review cycle whose evidence goes stale releases its held slots (P8: an ended cycle releases). Reverting the input makes the unit verified on the same evidence again, awaiting its confirmation, with no hold recreated. Two consequences, both reproduced on the unpatched engine (Wave 3.5 repair, ceiling 3, two units): if another unit's re-check takes the freed slot, the confirmation is refused `parent_ceiling` (`engine-explore.test.mjs` "P8 (Codex trace)", a D1-like halt, P8 holds); if room remains, the confirmation is accepted and spends from unheld allowance, as a `unit_confirmation` without `reserved: true`, which the oracle's P8 check above reports as a violation (and its P6 edit tracking also reports the edit and revert since the FAIL). No harness test or explored state reaches the second case today; it is not absorbed by an exception. The owner decides: restore the hold when the cycle is restored, refuse a confirmation whose hold was released, or record an exception.

Exception-handling note (no property violated): an exception thrown inside the unit-check runner's launch block (its `running` commit, the `unit-check-running` boundary) is caught by that block's catch-all and treated as a runner start failure: the unreleased runner is killed and the check is retried once (`UNIT_CHECK_RETRY`, no recheck spent). A SIGKILL there is a real crash and recovers as D6. `engine-crash.test.mjs` reports these points as `absorbed`; the recovered accounting equals the uncrashed run.

Ordering note (not a limit of any property): `gate ship-ready` reports `units_consumed_stale` before `candidate_mismatch`, and instead of `review_not_accepted` for a stale FAIL original; after the local proof ran, a stale unit conjunct (`units_unverified`, `unit_reviews_missing`, `units_consumed_stale`) is reported before the proof's `candidate_mismatch`; it refuses either way.

## What the Wave 3.5 harness does not show

- Power-loss durability (fsync ordering on a real crash of the machine).
- Behaviour under hostile workers (D7) and on Windows (D4).
- Directory declarations (D2, D3): the exploration and seeded worlds declare files only.
- Any state outside the bounded exploration: its explored-state and transition counts are printed by `engine-explore.test.mjs` and `engine-seeded.test.mjs`; "the exploration passed" means only "no violation in those states".
- Base-commit moves by dispatched or gate-run code other than the one directed case: a local-proof command making an empty commit (Wave 3.5 repair). Workers, RED runners and unit checks that move the base are not exercised.
- Buggy unit checks that write upstream (unit-less) paths: no world or stream does it.
- Malformed RUN-STATE bytes (a lone CR, a stray END marker, truncated JSON lines): the oracle parses RUN-STATE with its own lenient reader and no stream writes such bytes (earlier waves' own tests cover the known cases).
- The candidate id is computed by the production `candidate-id.mjs` CLI, not re-derived by the oracle: a bug there is shared by the engine and the oracle.
- Fingerprints are compared by content hash only: the oracle ignores file mode, so a permission-only change is not checked (see D2).
- P7: the oracle's tree walk skips `.specs`, so a repair writing under `.specs` outside its write set is not seen.
- P1: the oracle checks the approval binding only as it was before each command (pre-command plan and DAG); a binding change made by code the command ran is not compared after it.
- P6: the oracle does not independently compare the dependency-unit and base bindings of a confirmation with the FAIL's (it checks test edits, member re-runs, the repair's run and its candidate).
- Wave 2b-ii reviewer-role enforcement (cross-model second opinion of risky units, role identity) and check-time mutation (a check that changes its unit's files while running) are not fully asserted by the oracle; they rest on their own unit tests.
