# Effectiveness measurement of the vapt control catalog

AIS-HARNESS-4, Wave C part 2. Run on 2026-11-10 against the catalog with sha256
`ed41751ae3b4392d197d98aff78bbd0f6c0461ae7fe6c3f224bf32718899e5b4`. The catalog, its
evaluator and the engine were not changed in this wave.

The rules for this measurement are in [`prereg.json`](prereg.json). They were fixed, and
their hash posted on a public issue, before any fact writer, judge or scorer ran (see
`posted` in [`manifest.json`](manifest.json)). The posts cover the rules and the data files.
No post hashes the scorer's code, so they show that the rules came before the data, not when
the scorer first ran. Everything in the results block below is generated by `score.mjs` from
the committed data files; a test fails if the block and the data disagree.

## What was measured

The harness picks security controls for a change from facts about that change. This
measurement asks how well that works on real code:

1. An agent that never saw the controls wrote the facts for 24 real findings of one audited
   product, from the files the audit cites at the audited commit and the commit messages
   that wrote the cited lines. This is development data: the catalog's eight abuse controls
   were written from these same findings.
2. The same kind of agent wrote the facts for 24 public security advisories from other
   projects, from the code as it was before the fix. These were picked by a fixed rule with
   no human choice.
3. Two judges who never saw the facts or the selections marked, for every case and every
   control, whether a test of that control would have exposed the real weakness. A control
   counts as needed only when both said yes.
4. The scorer ran the catalog's own evaluator on the facts and counted.

Eleven of the 25 controls are selected for every kind of change ("always on"). Selecting one
of those shows nothing about selection, so the counts below look at the other 14 ("specific").

## Findings in plain words

- **The selector follows the catalog (R0).** Unchanged from Wave B: implementation fidelity,
  nothing more.
- **On real code the facts come out broad, and the catalog then selects almost everything
  (R1, R5; retrospective, in-sample, development data).** Per development case, between 22
  and 25 of the 25 controls were selected. Where the writer and the reference scenarios
  disagree, it is almost always the writer marking a fact true that the reference has false
  (66 cells, against 1 the other way).
- **Because of that, "the control written for this finding was selected" says little (R2;
  retrospective, in-sample, development data).** It was selected for all 22 findings that
  have one (the other 2 map to always-on controls), but so was nearly every other control.
- **Each group of findings depends on the controls written from it (R3; retrospective,
  in-sample, development data).** With a group's own controls removed, none of its findings
  was still caught by another specific control that both judges accept. With all eight abuse
  controls removed, the same holds for all 22.
- **The public advisories could not test the specific controls (R4).** In 10 of the 24 cases
  an always-on control was needed and selected. In the other 14 no control got a yes from both
  judges. No case needed a specific control, while the catalog selected 153 specific controls
  that were not needed and left out 183. By the rule fixed in advance, the statement is the
  one at the top of the results block.

So this measurement gives no evidence that fact-based selection keeps the controls a change
needs while leaving the others out. On the development cases (retrospective, in-sample,
development data) it selected nearly everything. On the public cases it did leave out
unneeded specific controls, but no case needed a specific control, so whether it would have
kept a needed one was not tested. It gives no evidence about the abuse controls outside the
product they were written from, and none against them either: the advisory set held no case
of that kind. It does not show whether any control's test would catch anything, because no
test was run.

## Reading the tables

- **R1** compares the new writer's facts with the 12 fixture scenarios that describe the same
  findings. It is agreement, not accuracy.
- **R2** asks whether the control the catalog names as written from a finding is selected
  from the writer's facts for that finding.
- **R3** removes controls and asks whether the findings of a group are still caught by a
  specific control that remains. "Partial only" means the judges saw a related control but
  not one whose stated attack would necessarily expose the weakness.
- **R4** counts, per public case and specific control, whether it was needed and whether it
  was selected, next to two fixed selectors: select everything, and select only the always-on
  controls.
- **R5** is how many of the 25 controls were selected per case.

## Limits

- Blindness is by instruction and an inputs-only folder, not enforced. The agents had file
  access; the deviations they reported are listed in `manifest.json`.
- On the development cases the fact writer never saw the controls, but the fact definitions
  it worked from contain examples taken from the same audit. R1, R2 and R3 are in-sample.
- The development ticket text is the messages of up to 8 commits, and the code is every cited
  file in full. That is broader than one real ticket, which is one reason the development
  facts are broad.
- The public cases have no ticket: the writer saw whole files as they were before the fix.
  Many are library code.
- Both judges are the same model family. Their agreement overstates independent agreement.
- The public set is 24 advisories published between 2026-10-30 and 2026-11-09. It is small
  and is not a random sample of weaknesses.
- Two of the public cases (C2-11 and C2-12) are separate advisories fixed by one commit. They
  have the same code and the same facts and are counted as two cases, as the rule allows.
- The development inputs (audit record, product files, commit messages) are local only. A
  reader of this repository cannot re-run that part or verify its recorded hash.
- A selected control is a planned test, not a caught weakness.

## Listed for follow-up (nothing was tuned in this wave)

- Facts written from real code select 22 to 25 controls per development case (retrospective,
  in-sample, development data). Whether tighter inputs, one commit's change instead of whole
  files, select fewer was not measured.
- 14 public cases have no control that both judges accept. By first-listed weakness type they
  are CWE-116, CWE-1333 (2), CWE-176, CWE-22 (1 of 2), CWE-248, CWE-400 (2), CWE-405, CWE-532,
  CWE-674, CWE-770 and CWE-835 (2).
- One development finding (F21) has no control that both judges accept, even with the full
  catalog (retrospective, in-sample, development data).
- The abuse controls have not been scored on any case from outside the audited product. A
  corpus with business-logic weaknesses is needed for that, for example the findings of a
  `security-audit` run on another product, scored with the tools in this folder.
