# S6 design v3: one fenced scope-contract block (DESIGN ONLY, base 82ec937)

Status: proposal for review. Nothing is implemented, committed or pushed, and this file is untracked scratch.
Scope: S6 files only (`check-pr-scope.mjs` and its test, `plan.md`, `review.md`, `ship.md`). The design adds no
engine, gate or RUN-STATE authority change, no new event, no protected-file change and no runtime dependency.

## 1. Representation

The block is three raw lines, each starting at column 0, with a blank line before and after it:

    ```scope-contract
    {"v":1,"mode":"manual","dag":null,"planned":["src/checkout","src/checkout/page.tsx"],"supporting":["tests"]}
    ```

- **Opener:** exactly `` ```scope-contract ``. **Closer:** exactly ```` ``` ````. Each line ends in LF or CRLF.
- **Body:** one canonical JSON line, with rules unchanged from 82ec937:
  - key order `v, mode, dag, planned, supporting`, and `JSON.stringify(JSON.parse(x)) === x`;
  - engine caps 256 entries of at most 512 chars and 64 KiB; manual caps 64 entries of at most 256 chars and 8 KiB;
  - entry charset printable ASCII without `` < > & ` | " ``.
- **The body cannot be a closer** (it has no backtick). CommonMark shows fenced content literally: no emphasis, no
  links, no entities, no inline HTML.

## 2. Rules (raw text, no Markdown parser)

Call the file `F`. The narrative is `F` minus the RUN-STATE body; the markers stay in it, as with
`planNarrativeDigest`.

**R0 Characters (whole F).**
- Allowed controls are TAB, LF and CR only when it is immediately followed by LF. Everything else below is refused
  (`scope_contract_unsafe`), anywhere in F, the RUN-STATE body included:
  - C0 controls `\x00-\x08`, `\x0b`, `\x0c`, `\x0e-\x1f` (this includes NUL and ESC);
  - DEL `\x7f`;
  - C1 controls `\x80-\x9f` and U+0085;
  - U+2028, U+2029 and BOM U+FEFF.
- Then split on `\r?\n`. That split equals CommonMark's `\r\n|\r|\n`, and no terminal escape sequence survives.
- A line is blank iff it matches `^[ \t]*$`.
- Measured: 0 of 15 real plans contain any of these characters.

**R1 Exactly one block.**
- Exactly one line equals the opener; the next line is the body and the next one equals the closer.
- No opener is `scope_contract_missing`, with a hint when a legacy `scope-contract: ` line exists.
- A second opener is `scope_contract_ambiguous`. A wrong body or closer is `scope_contract_malformed`.

**R2 The key appears nowhere else.**
- No other line of F contains `scope-contract`, compared case-insensitively. A hit is `scope_contract_ambiguous`.
- Encoded spellings (`&#45;`, `\-`) are NOT pattern-matched here. They are made impossible by R3b, because an
  alias is dangerous only as a fence info string.

**R3 Fences.**
- **R3a (before the closer):** no line other than the opener contains a run of 3+ backticks or 3+ tildes ANYWHERE in
  the line.
- **R3b (whole F, outside the three block lines):** no line, after stripping the container prefix
  `^(?:[ \t]*(?:>|[-+*](?=[ \t]|$)|\d{1,9}[.)](?=[ \t]|$)))*[ \t]*`, BEGINS with 3+ backticks or 3+ tildes. This
  covers the RUN-STATE body and lines after the block.
- Both refuse with `scope_contract_unsafe`.
- **Consequence:** the document holds exactly ONE fenced code block of any kind, namely ours. A decoded-alias second
  block (`` ```scope&#45;contract ``, `` ```scope\-contract ``, `~~~`, `> ```x`) cannot exist, whatever its info
  string decodes to. This holds by construction, not by an alias list.
- **Cost:** a plan may hold NO other fenced code block anywhere. Examples use 4-space indented code, which is not a
  fence and cannot carry an info string, or inline code. Measured: 1 of 15 real plans has fences.

**R4 Position.** The closer lies before `<!-- RUN-STATE:BEGIN -->`, or the file has no RUN-STATE (lint draft mode,
§7). Otherwise the refusal is `scope_contract_unsafe`.

**R5 Isolation.** The line before the opener is blank, and so is the line after the closer (or end of file). There
is no exception after front matter.

**R6 HTML blocks before the opener (CommonMark 0.31.2 §4.6).**
- The spec text is pinned verbatim in a test comment, and the implementation is diffed against it.
- The rule is evaluated on each line before the opener after the R3b container strip. The `>` branch needs no
  following whitespace, so `><script>` is stripped too.
- **Types 1–5** must reach their end condition on a line strictly before the blank line that precedes the opener:

| Type | Start condition | End condition |
|---|---|---|
| 1 | `<pre`, `<script`, `<style` or `<textarea` (case-insensitive), followed by a space, a tab, `>` or end of line. Superset: any character outside `[A-Za-z0-9-]` | a line containing `</pre>`, `</script>`, `</style>` or `</textarea>` (case-insensitive; the name need not match the opener) |
| 2 | `<!--` | `-->` |
| 3 | `<?` | `?>` |
| 4 | `<!` followed by an ASCII letter | `>` |
| 5 | `<![CDATA[` | `]]>` |

- **Types 6 and 7** end at the next blank line, and R5 guarantees one:
  - type 6 is a block-tag name from the spec list, followed by a space, a tab, end of line, `>` or `/>`;
  - type 7 is a complete open tag (any name except pre, script, style, textarea) or a closing tag of ANY name,
    followed only by spaces and tabs. Type 7 cannot interrupt a paragraph.
- **Other ways a block ends**, noted from the spec: a block also ends when its container closes or at end of
  document. The superset simply demands the end string earlier, so neither case can leave a block open at the
  opener.

**R7 Front matter.**
- Trigger: line 1 STARTS with `---` or `+++`. This covers gray-matter `---yaml` and `---json`.
- The closer is the first later line equal to `---` or `+++` (the same family) after stripping trailing spaces and
  tabs. It must lie before the opener, with a blank line between (R5).
- A `...` line before the closer refuses.
- No front-matter line holds the key (R2) or a fence (R3).
- Residuals: Hugo `;;;` and `{` front matter (§13).

**R8 Math.** No line before the opener contains `$$`.

**R9 DOM rule (option A only, §5).** Any `<` followed by `[A-Za-z/!?]` anywhere in F refuses. The only exempt lines
are the exact RUN-STATE markers and `^<!-- security-plan: \{[^<>]*\} -->$`.

**R10 Scope-digest line.**
- Exactly ONE narrative line before RUN-STATE matches `^scope digest: sha256:[0-9a-f]{64}$`.
- The hash is SHA-256 over the UTF-8 bytes of the body line, excluding its LF or CRLF terminator.
- It must equal the body's hash; otherwise `scope_digest_mismatch`. Missing or duplicated is
  `scope_digest_missing` or `scope_digest_ambiguous`.
- It is required, and its bytes are bound by the START digest.

## 3. What is PROVEN (structural)

Claim: under R0–R8 and R3b, both CommonMark 0.31.2 and GFM produce EXACTLY ONE fenced code block in the whole
document. It is document-level, its info string is `scope-contract`, and its content is the body plus LF.

1. **Line model.** R0 leaves only LF and CRLF terminators, so the line indices agree with any parser's.
2. **Uniqueness.** By R3b, no other line can open a fence of any kind or in any container. By R1, there is exactly
   one opener line.
3. **Open at the opener:**
   - no fence is open, by R3a;
   - no HTML block of types 1–5 is open, by R6;
   - types 6 and 7 have ended at the blank line (R5);
   - no paragraph is open (R5);
   - the opener is not indented code and not in a container: it is at column 0, with no `>` or list marker; lazy
     continuation needs an open paragraph, and a list item needs indentation greater than 0;
   - front matter is closed (R7) and no `$$` precedes it (R8).
4. **Exact content.** The info string has no backtick and the body has no backtick. The closer is three backticks
   at column 0, the length of the opener.
5. **Nothing later changes it.** Block structure is decided in order, and by R3b nothing after the closer can form
   another fence.

**Evidence:**
- Opus: 2 × 200k fuzz against markdown-it 14.1.0 and commonmark 0.31.2, no structural survivor of v2.
- Codex's alias survivor broke uniqueness after the block. R3b closes that by construction.
- The frozen corpus (§10) pins all of this as regressions.

## 4. What is NOT proven

- **DOM and CSS rendering** in a viewer that passes raw HTML into a page: an unclosed `<div hidden>`, a `<style>` or
  a script can hide or restyle the block without changing Markdown structure.
- **Renderer extensions** (MDX, Liquid, directives, admonitions) and non-YAML front matter (Hugo `;;;`, `{`).
- **The approval artifact.** No script sees the ExitPlanMode request or the screen. §6 makes verification
  mechanical for the reviewer, but running it is a HUMAN or orchestrator step.
- **Owner understanding** of `mode` and of supporting paths lying outside the Design Contract (the S3c step).

## 5. D-A: the three options

Measured on the 15 real plans in `.specs/plans` at 82ec937:

| Option | Rule | Real plans refused | Residual |
|---|---|---|---|
| **A** | R9 whole-file tag refusal, exact-line exemptions only | 10/15 (`<placeholder>` in CLI usage and prose; instruction comments in RUN-STATE) | extensions only |
| **A-cheap** (Codex) | A, but a tag is also exempt on a column-0, blank-isolated line that is entirely one code span: two delimiter backticks, none inside, no escaped opener | 10/15. The failing tags sit inside prose and table lines, never on isolated span lines, so the exemption saves nothing | the same as A. Sound: such a line is a paragraph holding one code span, and a code span is literal |
| **B** | no R9 | 0 refusals for HTML | an HTML-rendering viewer could hide the block. Closed by the written policy below and by the quote byte-verification (§6) |

- **Recommendation: B with the policy**, which Opus and Codex both recommend conditionally. A costs 10 of 15 real
  plans, and A-cheap does not reduce that.
- **B deliberately REMOVES the 82ec937 global HTML restriction.** Under B, raw HTML anywhere in a plan is no longer
  refused by S6. Only R0–R8, R3b and R10 remain.

**Written owner policy for B (text for the owner to sign):**

> I approve a plan's execution scope only from a trusted, complete and untruncated literal presentation of the
> ExitPlanMode request in a terminal. In that presentation HTML and Markdown extensions neither execute nor suppress
> content, and terminal control sequences are escaped or absent. The request shows the scope block inside a
> four-backtick fence. Before any build, the displayed body is verified with `check-pr-scope.mjs contract
> --verify-quote` against the plan block and the record (the same bytes and the same SHA-256). Any other view of a
> plan, including browser previews, GitHub rendering or editor previews, is never approval. A plan whose quote fails
> verification is not approved.

If the owner will not sign it, choose A.

## 6. Second control: quote byte-verification (human or orchestrator boundary)

- **`contract`** prints:
  1. the three-line block;
  2. the QUOTE TEXT: the block inside a four-backtick outer fence;
  3. `scope digest: sha256:<hex>`, the R10 line to paste into the plan.
- **The ExitPlanMode request** contains the quote text verbatim. The orchestrator saves the request text it sent
  to a file under the git dir, for example `<git dir>/ai-skills/ship-ticket/<T>.approval-quote.txt`.
- **`contract --verify-quote <file> --plan <plan> [--record <scope.json>]`:**
  1. Extract the single four-backtick-fenced block from the file; anything other than exactly one is FAIL.
  2. Take its inner body line BYTES.
  3. Compare them byte for byte with the plan block body and, if given, with `record.contract`.
  4. Recompute the SHA-256 of each and check it against the plan's R10 line and `record.contract_sha256`.
  5. Print PASS or FAIL with the first differing byte offset. Exit 0 or 1.
- **The record** carries `contract` (body bytes) and `contract_sha256`, printed at REVIEW and SHIP.
- **Stated plainly:** the script cannot know that the saved quote file is what the owner saw. Saving it and running
  `--verify-quote` is an orchestrator step, and the reviewer re-runs it. Hashes are never compared alone: the BODY
  BYTES are compared, so a stated hash cannot be paired with a different body.
- **The 64 KiB problem:** a large engine contract is compared by `--verify-quote` and by `contract_dag_mismatch`,
  not by eye.

## 7. Binding and the commands

- **`lint --plan P`** (no git, no START):
  - It applies R0–R8, R3b, R9 if option A, R10, and the canonical and field rules, to the whole file.
  - With RUN-STATE markers present it also validates the body (R0, R2, R3b, R9). With none it reports "draft".
  - It prints the `contract` output. Exit 0 or 2.
- **`check`** runs the same function on the exact bytes of the file whose narrative digest equals the last START of
  the run (`approval_mismatch` otherwise), at REVIEW and again at SHIP.
- **RUN-STATE body changes after approval** are digest-excluded, so they are re-validated by R0, R2, R3b and R9 on
  every `check`.
- **`contract`** builds or verifies standalone, without a plan or RUN-STATE.

## 8. Migration

- **No silent conversion.** A legacy bare line, or no block, is `scope_contract_missing` with a hint. It needs a new
  plan version and re-approval.
- **All mode tripwires stay:** `dag_required`, `dag_unbound`, `contract_dag_mismatch`, `contract_mode_mismatch`,
  `manual_with_engine_evidence`, and engine-to-manual only through re-approval.
- **`plan.md` template:**
  - the outer ```` ```markdown ```` fence becomes ````` ````markdown `````;
  - the inner three-backtick block and the `scope digest:` line go under the DAG table, with blank lines around them.
- **The template conflicts with R3b, and copying it is the hazard.** The reference doc's own outer fence is fine,
  because `plan.md` is not a plan. But a plan copied from it must not carry any other fence. The template prose says
  so, and `lint` enforces it.
- **`review.md` and `ship.md`:** `--verify-quote` is required at REVIEW and SHIP (orchestrator-run, reviewer
  re-run). The documents state the human boundary and the B policy, if chosen.

## 9. Usability disclosure

- **R2:** `scope-contract` can appear nowhere else, including paths such as `src/scope-contract.ts`. Confirmed:
  such a path can be neither mentioned nor planned.
- **R3a and R3b:** no other fenced code block anywhere in the plan (1 of 15 real plans has fences), and no inline
  triple backticks before the block. Examples go in 4-space indented code.
- **R5 and R7:** a blank line before the block, even after front matter. All 14 real front-matter plans close with
  `---`.
- **R8:** no `$$` before the block. **R10:** one required `scope digest:` line.
- **Option A or A-cheap:** 10 of 15 plans refused. **Option B:** none.
- **Pre-approval `lint`** turns all of these into authoring-time errors.

## 10. Tests

- **Frozen two-parser corpus (regression evidence, NOT a live oracle):**
  - The generator script is pinned and documented in the test file header: path, parser versions (markdown-it
    14.1.0 with `{html: true}`; commonmark.js 0.31.2 with default options, HTML enabled), seed, and the snippet
    alphabet.
  - It needs a one-time scratch `npm install` (D-net).
  - It emits about 300 documents with `{fences: count, top_level, info, content}` per parser. markdown-it's info is
    normalized (`token.info.trim()`, entity and escape decoding as markdown-it does).
  - The documents include both decoded aliases (`scope&#45;contract`, `scope\-contract`) and every survivor from all
    rounds.
  - The test embeds the corpus with its sha256. It asserts that every checker-ACCEPTED document has, in both parsers,
    exactly one fence in the whole document, with info `scope-contract`, content `body + "\n"`, at top level, and
    that every document a parser renders otherwise is REFUSED.
  - Limitation, stated: it proves agreement on the corpus only. New inputs rely on §3.
- **Optional live-oracle script** (`scratch/live-oracle.mjs`, not in CI): runs the checker against both parsers on
  random documents. It is kept for re-verification after any rule change.
- **DOM tests:** under A, the R9 cases. Under B, the hostile-HTML cases are asserted ACCEPTED, so the removed
  restriction is explicit and pinned.
- **Regressions:**
  - Markdown rendering: `apps/*/src`, `__tests__`, `src/[safe](hidden)`, `$$`;
  - front matter: with a BOM, the `...` closer, `---yaml`, `---\n<div>\n---\nC`;
  - raw HTML: `<script\t>`, `> <script>`, `><script>`, a script in RUN-STATE, the escaped-backtick `<style>`, the
    HTML wrappers, `<TICKET>`, Codex's JSON `<!--`, entities;
  - line breaks and controls: a lone CR, ESC `\x1b[8m`, each C0 and C1 class;
  - fences: an alias fence after the block (both spellings), `~~~` after the block, a fence in RUN-STATE,
    container-prefixed fences, a 4-backtick vs 3-backtick fence;
  - digest and quote: a duplicated or wrong `scope digest:` line, and a quote with a matching stated hash but a
    different body (`--verify-quote` FAIL);
  - the table-era cases.
- **Properties:** the ≥5000 malformed-declaration property on the block, and a hostile-assembly property checked
  against the frozen corpus rules.

## 13. Residuals (honest)

1. **Under B:** HTML or DOM rendering in a non-terminal viewer, excluded by the signed policy, not by code. **Under
   A:** extensions only.
2. **Extensions and non-YAML front matter** (Hugo `;;;`, `{`): no rule. Under B the policy limits approval to the
   terminal view.
3. **The approval artifact:** the saved quote file is trusted to be what the owner saw. `--verify-quote` makes the
   comparison mechanical, not the provenance.
4. **The frozen corpus is regression evidence only;** the R6 table is pinned against the spec text.
5. **Author restrictions:** R2 (key and paths), R3 (no other fences anywhere), R10 (the digest line).
6. **Owner understanding** of mode and supporting paths (S3c).
7. **Last-START reading and plan-file writability** (S-20, S-23, S-25).
8. **candidate-id prefix exclusion matching:** an engine-owner follow-up.
